# hanno-tourism.jp `news` 投稿タイプ対応 設計

作成日: 2026-08-10

## 背景

`cal-tourism-fetch` が巡回しているのは投稿タイプ `tour` (`/hanno-eco/tour/<slug>/`) だけで、
祭り・花火・盆踊りなどの単発イベント告知が載る `news` (`/news/<slug>/`) は対象外だった。
2026-08-08 の「はんのう昭和盆踊り」を取りこぼしている (告知は前日 15:18 に `news` へ公開)。

実装前に 137 件の実データを調査した。結果は「決定論パーサ単独では実用にならない」。

### 調査結果 (2026-08-10 時点、実測)

| 項目 | 実測値 |
|---|---|
| `news` 総件数 | 137 (最古 2017-09-21、最新 2026-08-07) |
| イベント系タグ (`イベント`/`飯能まつり`/`エコツアー`) | 69 |
| `日時:` / `期間:` / `開催日:` の定型ラベルあり | 69 件中 13 (19%) |
| 正規表現で本文から日付を 1 つ以上取得 | 69 件中 45 (65%) |
| うち曜日カッコ一致で年まで確定 | 69 件中 39 (57%) |

再現率は悪くないが適合率が低い。2026 年イベント系 18 件を手で突き合わせたところ、
開催日として正しかったのは約 1/3。`tour` の `<dl><dt>開催日・時間</dt>` に相当する
構造が `news` には無く、あっても以下の理由で嘘になる。

**確認された失敗モード (すべて実データ):**

1. **更新スタンプの誤取得** — 「6/16更新」「4/11更新」はカレンダー画像の更新日。
   キッチンカー記事 4 件中 3 件はこれしか日付が無く全滅。
2. **中止が本文に埋め込まれる** — 名栗ほたる祭りは冒頭が「【6/26更新】台風接近に伴い
   中止が決定しました」だが、下に「日時:2026年6月27日(土)」がそのまま残る。
3. **「中止」キーワードは判定に使えない** — イベント系 69 件中 10 件が該当するが、
   8 件は「雨天決行・荒天中止」の定型文。実際の中止は 1 件。
4. **延期後も旧日程が残る** — エコツアーガイド養成講座は「延期となりました」の下に
   旧日程「5月30日(土)」。曜日一致による年推定が 2025 年を「検証済み」として誤確定した。
5. **終了日を開催日として拾う** — ムーミン谷みずあそび →「9月6日(日)まで」。
6. **副イベントの日付を拾う** — 飯能ひな飾り展は本体 2/24〜3/8 だが、協賛イベント
   「丸太雛めぐり」の 2/22 が本文中で先に現れる。

### 掲載制御について

README には「`tour-month` に相当する掲載制御が無い」と書いていたが、`tag-news`
タクソノミーが部分的な代替になる。

| id | 名称 | slug | 件数 |
|---|---|---|---|
| 4 | おしらせ | `info` | 74 |
| 6 | イベント | `event` | 55 |
| 7 | 飯能まつり | `hanno-matsuri` | 2 |
| 8 | エコツアー | `ecotour` | 14 |
| 77 | 奥むさし飯能観光協会 | `tourism-association` | 41 |

休業・営業案内はほぼ全て `おしらせ`/`協会` のみのタグで、イベント系で絞ると休業ノイズは
ほぼ全滅する。ただしこれは「種類」であって「現在有効か」ではない。本設計では掲載可否の
判定には使わず、表示用の絵文字選択にのみ使う。

## 方針

**告知と本番の 2 系統を出す。**

- **告知エントリ**: 記事が公開された事実。`dtstart` = 記事の公開日。掲載日は事実そのもの
  なので嘘をつきようがない。`cal-oshirase-fetch` が市サイトで担っている役と同じ。
- **本番エントリ**: 開催日。抽出の当たり外れはこちらだけが引き受ける。

これにより「確信が持てないとき掲載日にフォールバックする」という妥協が不要になる。
開催日が取れなければ告知だけが残る。

### 確定した判断

| 論点 | 決定 |
|---|---|
| 告知の対象範囲 | `news` 全件 (タグ付け漏れが実測 2 件あるため) |
| 本番の対象範囲 | 日付が取れたら全件 (休業・営業情報も市民には有用。判定ロジックを持たない) |
| 本番の判定 | LLM 抽出 + 機械検証の二重チェック。両方通過時のみ作成 |
| 中止・延期への追随 | 既存の本番を残し `summary` を `【中止】…` に書き換える |
| 中止として生まれた記事 | 本番を作らない (告知のみ)。新規に中止済みの予定を作っても役に立たない |
| 手動 YAML との衝突 | 手動を優先しクローラは本番を作らない。告知は作る |
| 初回実行の遡り | 直近 6 ヶ月 (`--backfill-months`、既定 6) |
| 記事削除への追随 | スコープ外。API から消えても既存 YAML は残す |

## アーキテクチャ

### 構成

- **新規** `calendar/bin/cal-tourism-news-fetch`
- **共通化** `calendar/bin/_lib.py` に `call_llm(system, user, model, max_tokens)` を追加し、
  `cal-oshirase-fetch` の `summarize_with_llm` / `diff_with_llm` をこれに載せ替える。
  既存の挙動は変えない。プロンプト本体は各スクリプトに残す (内容が全く異なるため)。
- **設定** `calendar/sources.yaml` に `tourism-news` エントリを追加。

```yaml
tourism-news:
  uid_prefix: tourism-news
  source_type: hanno-tourism-jp-news
  summary_prefix_notice: "📢 "     # 告知エントリ
  summary_prefix_event: "🎪 "      # 本番エントリ (イベント系タグ)
  summary_prefix_other: "ℹ️ "      # 本番エントリ (それ以外)
  api_url: "https://hanno-tourism.jp/wp-json/wp/v2/news"
  url_host_allowlist: hanno-tourism.jp
  url_path_prefix: "/news/"
  backfill_months: 6
```

`_lib.py` を分離した理由は責務分離そのものより、LLM 呼び出しが 3 本目になる事実。
2 本目までは複製で許容範囲だったが、3 本目は共通化の閾値。API 呼び出し部の修正
(リトライ・タイムアウト) が片方だけ当たる事故を防ぐ。

`cal-tourism-fetch` に相乗りさせない理由: 共有できるのは REST API 取得と `modified_gmt`
キャッシュ判定で合計 30 行程度だが、分岐は掲載制御・日付抽出・エントリ生成の全段に入る。
1 ファイルが 900 行超になり、tour 側の回帰リスクを news の変更が背負う。

### データフロー

```
GET /wp-json/wp/v2/news?per_page=100&page=1..2     ← 2 リクエストで全件
        ↓  date_gmt >= 今日 - backfill_months で絞る
        ↓  .http-cache.json の modified_gmt と比較 → 変化なしはスキップ
        ↓  変化あり・新規のものだけ LLM へ (1 記事 1 回)
        ↓  機械検証
   ┌────┴────┐
 告知エントリ      本番エントリ
 dtstart=公開日   dtstart=抽出した開催日
 uid: tourism-news-<id>       uid: tourism-news-<id>-event
 全件作る          検証通過 かつ 手動 YAML と非衝突 の場合のみ
```

`<id>` は WordPress の投稿 ID (API の `id`)。slug は日本語のパーセントエンコードで
長大になるため使わない。

告知エントリの `dtstart` は `date_gmt` を JST に変換した日付。

`--backfill-months` は初回だけでなく毎回適用するフィルタ。6 ヶ月より古い記事が更新されても
処理しない。「古い記事の更新を追う」ことに実益が薄く、条件分岐を増やしたくないため。

**HTML の取得は不要。** `content.rendered` が API に露出しているため、全件が REST API
2 リクエストで完結する。`tour` は日程が ACF 由来で API に出ないため HTML の二段取得が
必要だったが、`news` にはその制約が無い。

日次 CI での定常コストは、変更 0 件なら API 2 リクエストのみ・LLM 呼び出し 0 回。

### 期間イベント

`dtstart` / `dtend` の範囲 1 件で出す。手動の夏祭り YAML は 7/18・7/19 を別ファイルに
していたが、さくらウィーク (3/28〜4/5 の 9 日間) を 9 ファイルにするのは過剰。

## LLM インタフェース

モデルは `claude-haiku-4-5` (oshirase と同じ)。1 記事 1 回、JSON を返させる。

```json
{
  "summary": "…200〜400字…",
  "event_date": "2026-08-08",
  "event_end_date": null,
  "date_evidence": "日時:2026年8月8日(土)",
  "status": "normal"
}
```

`status`: `normal` / `canceled` / `postponed` / `ended`

### プロンプトで潰す点

調査で踏んだ 6 つの失敗モードに一対一で対応させる。

| 実データ | 指示 |
|---|---|
| キッチンカー「6/16更新」 | 更新スタンプは開催日ではない |
| みずあそび「9月6日(日)まで」 | 終了日は `event_end_date`。開始日が本文に無ければ `event_date` は null |
| ひな飾り展 2/22 (丸太雛めぐり) | 副イベント・協賛イベントではなく記事の主題の日付 |
| 名栗ほたる祭り | 冒頭の中止追記は `status` に出す。`event_date` は元の開催日のまま返す |
| 養成講座「延期となりました」 | 同上 (`postponed`) |
| 飯能まつり協賛のお願い | 記事の主題が募集でも、本文に明記された開催日は返す |

`summary` の方針は `cal-oshirase-fetch` の `LLM_SYSTEM_PROMPT` に準拠する
(Markdown 禁止、200〜400 字、ステータスを要約に必ず含める、推測禁止)。

### 機械検証

以下 5 項目すべてを通過して初めて本番を作る。

1. `date_evidence` が正規化本文に部分文字列として実在する ← 幻覚検出
2. `event_date` の月日が `date_evidence` 内に現れる ← 根拠と結論の一致
3. `date_evidence` に曜日表記があれば `event_date` の曜日と一致する
4. `event_date` が記事公開日の −31 〜 +400 日の範囲
5. `date_evidence` が更新スタンプパターン `\d{1,2}/\d{1,2}\s*更新` に一致しない

項目 3 は調査時に「曜日チェックサムが誤った年を*検証済み*として確定させた」失敗をしている
(養成講座が 2025 年に滑落)。あれは正規表現が候補年を総当たりしたためで、LLM が返した
1 個の日付を検算する用途では逆向きに効く。項目 4 を併用して過去年への滑落を止める。

失格時は本番を作らず、理由を stderr に出す。告知は作る。

### 検証とは独立した本番の作成条件

上記 5 項目は「取れた日付が信用できるか」の検査であって、作成可否の全部ではない。
以下は検証と直交する条件として別に判定する。

| 条件 | 挙動 |
|---|---|
| `event_date` が null | 本番を作らない (告知のみ)。`event_end_date` だけある「開催中」記事もここに入る |
| `status` が `canceled`/`postponed` かつ既存の本番が無い | 本番を作らない (告知のみ) |
| `status` が `canceled`/`postponed` かつ既存の本番がある | 既存を `【中止】` に書き換える |
| 同じ記事を指す手動 YAML がある | 本番を作らない (告知のみ) |

`event_end_date` は `event_date` が取れている場合にのみ `dtend` として使う。

### 正規化

`_lib.normalize_fullwidth_digits` などを使うが、**囲み曜日文字 (㈪㈫㈬㈭㈮㈯㈰、㊊〜㊐) の
変換を `_lib.py` に追加する**。「飯能河原6/27㈯・28㈰の営業について」が実在する。

### LLM が使えない場合

API キーが無い環境では `cal-oshirase-fetch` と同じく degrade する。告知のみを出し、
`description` は本文をそのまま使う。本文が長い場合の扱いも oshirase に合わせ、
`FULL_TEXT_THRESHOLD` (oshirase では 400 字) 以下ならそのまま、超える場合は
先頭から切り詰めて末尾に元記事への誘導を付ける。本番は作らない。

LLM 呼び出しが個別に失敗した記事も同じ扱い (告知のみ)。全件失敗した場合だけ exit 2。

## 更新・冪等性

**冪等性**は `modified_gmt` で担保する。`.http-cache.json` に相乗りし、処理が成功した
記事だけ記録するので、失敗分は次回リトライされる。

**更新時の挙動**は告知側と本番側で分ける。

- **告知エントリ**: `cal-oshirase-fetch` の世代リンク機構を流用する。前世代を残し
  「主な変更」1 行を付ける。中止追記はここに自然に出る。
- **本番エントリ**: `status` が `canceled` / `postponed` に変わったら `summary` を
  `【中止】…` に書き換え、`description` 冒頭に理由を置く。`_lib._rewrite_yaml_scalar`
  系を使う。

**手動 YAML との衝突検出**: 既存の `calendar/events/**` を走査し、`url` または
`source.url` が同じ news 記事を指す YAML があれば本番を作らない。手動の夏祭り YAML は
URL がパーセントエンコード済み (`…/news/%E4%BB%A4%E5%92%8C…`) で API の `link` も同じ
形式だが、**一致判定はデコードして正規化してから行う**。エンコード表記の揺れで衝突を
見逃すと重複が出る。

現時点で該当する手動 YAML は 2 件:
`calendar/events/2026/07-18_natsumatsuri-20260718.yaml`、
`calendar/events/2026/07-19_natsumatsuri-20260719.yaml`。

## サニティチェック

| 判定 | 扱い |
|---|---|
| `--min-news` (既定 100) | API の返す件数がこれ未満なら exit 2 |
| LLM 全件失敗 | 呼び出しが 1 件以上あり全件 JSON パース不能なら exit 2 |
| 抽出失敗率 | **判定に使わない**。ログ出力のみ |

`--min-news` を 100 と高めに置けるのは、`news` が蓄積型で 2017 年の記事も残っている
ため (実測 137 件)。大量に消えるのは異常事態と見なせる。

抽出失敗率を判定に使わない理由: `tour` の「取得したページが 1 件以上あり全件 0 セッション
なら exit 2」は、tour が全て日程付きイベントだから成立していた。`news` は休業案内・
会報誌発行など**日付が無いのが正常な記事**を含み、告知は全件対象と決めている。ある日の
更新分がたまたま全部そういう記事だったときに誤発火する。

## テスト

既存の作法に合わせる (`test_tourism_api.py` は `fetch_json` を差し替えてネットワーク
非依存、`capture-fixtures` は手動実行のネットワークツール)。
**LLM はテストで実呼び出ししない。** 非決定的なので記録した応答を再生する。

### 層 1: 機械検証のユニットテスト

`call_llm` を差し替え、検証 5 項目を個別に落とすケースを作る。幻覚 (`date_evidence` が
本文に無い)、根拠と結論の不一致、曜日不一致、範囲外の年、更新スタンプ。

### 層 2: 実データ由来の回帰フィクスチャ

API レスポンスは実物を `calendar/tests/fixtures/cal-tourism-news-fetch/` に保存する。

| フィクスチャ | 期待する結果 |
|---|---|
| はんのう昭和盆踊り | 本番 2026-08-08 を作る |
| キッチンカー (6/16更新) | 検証 5 で失格 → 告知のみ |
| ムーミン谷みずあそび | `event_date` null → 告知のみ |
| 飯能ひな飾り展 | 2026-02-24 (副イベント 2/22 ではない) |
| 名栗ほたる祭り | `canceled` → 既存本番を【中止】に書き換え |
| エコツアーガイド養成講座 | `postponed`、かつ 2025 年に滑落しない |
| 令和8年飯能夏祭り | 手動 YAML と URL 衝突 → 本番を作らない |
| 観光案内所 休業のお知らせ | 本番を作る (全件方針の確認) |

### 層 3: ゴールデンテスト

API レスポンスと記録済み LLM 応答から YAML 全体を生成し、既存の `run-golden` に載せる。

### 検証していないこと

層 2 は「記録済み LLM 応答に対して**コード側**が正しく振る舞うか」を見るもので、
**プロンプトを変えたとき LLM が正しく答えるかは検証していない**。`cal-oshirase-fetch` が
`DESCRIPTION_FORMAT_VERSION` を 8 まで上げているのと同じで、プロンプト改訂の効果は
実データで手動確認するしかない。

そのため調査で使った 137 件の API レスポンスを `calendar/tests/seed/` に置き、プロンプト
改訂時に手で回せる評価スクリプトを添える。評価スクリプトは CI に載せない (LLM を実呼び出し
するため)。

## 実装後の変更 (2026-08-10 追記)

**この文書は設計時点の記録**。実装して実データを流した結果、以下がここでの記述と
変わっている。現在の仕様は `calendar/README.md` が正。

いずれも「テストは通るが実データで壊れる」類で、実際に動かして初めて分かった。

| 変更 | 理由 |
|---|---|
| 機械検算が **5 項目 → 6 項目** | 和暦換算のチェックを追加。LLM が「令和8年4月1日」を 2027-04-01 と換算し、曜日表記が無いため検算 3 で拾えず範囲チェックもすり抜けて、誤った日付が実際に通っていた |
| 照合対象を **本文 → 公開日 + タイトル + 本文** | LLM にはタイトル込みで見せているのに本文だけで照合しており、日付がタイトルにしか無い記事を取りこぼしていた |
| LLM に **公開日を渡す** | プロンプトは「年が無ければ公開日から推定せよ」と指示しているのに公開日を送っていなかった。40 件中 5 件が過去年に滑って失格していた |
| 照合時に**引用符を ASCII に畳む** | 「そのままコピー」と指示しても LLM は `“宵宮”` を `"宵宮"` と打ち直す |
| **`short_body` と `llm_fail` を分離** | 本文が薄い記事 (チラシ) の意図的スキップを失敗に数え、変更分が全部チラシだった日に「全件失敗 = API 障害」と誤判定して CI が exit 2 した。この文書自身が「抽出失敗率を判定に使うと誤発火する」と書いていたのに、隣の判定に同じ穴を開けていた |
| **`announces_event_itself` を追加** | 「飯能まつり 協賛のお願い」から 11/7 の本番が作られ、当日欄に「協賛のお願い」と出た。タイトル語のパターンでは判別できず LLM 判定にした。**唯一機械検算できない判定** |
