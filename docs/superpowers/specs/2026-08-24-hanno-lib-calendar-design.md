# 飯能市立図書館 カレンダー — 設計

ステータス: 設計 (2026-08-24 起案)。実装は未着手。

## 1. 背景

飯能市立図書館 (`www.hanno-lib.jp`) の**休館日**と**イベント**を取り込み、
館ごとに独立したカレンダーとして配信する。

図書館は市民の利用頻度が高い施設でありながら、いま city-tecoli 側では Google
Places の `regularOpeningHours` から出る開館状態しか持っていない。特別整理期間
や臨時休館のような**例外は Places に載らない**。イベント (おはなし会、こども
図書館まつり) に至っては経路が無い。

こども図書館から着手する理由は、飯能を知らない人への訴求力が子ども向けの内容に
あるため (2026-08-21 の判断)。ただし本館の休館日も同時に取り込む。

### この設計の前提となる調査

2026-08-23〜24 に実施。`calendar/README.md`「配信元を最初に見る」の手順に沿う。
**観測は腐るので README には残さない**。ここに残すのは設計判断の根拠として
必要な範囲に限る。

## 2. 取り込んでよいか (step 0)

`robots.txt` は 404、利用規約ページは無く、あるのはプライバシーポリシーのみ。
飯能市の施設なので **`city.hanno.lg.jp` と同じ扱い**とする。すなわち
`docs/ai-content-policy.md` の「リンク + 部分要約という現実的な再配信、出典明示、
苦情が来たら柔軟に削除・修正」で運用する。

`robots.txt` の 404 は許可ではない。上記は「市の施設であり、既に市サイトを同じ
方針で取り込んでいる」ことを根拠にした判断であって、サイト側の明示的な許諾では
ない。

**画像は取り込まない。** 詳細ページには `/calendar/images/*.jpg` があるが、
利用条件の記載が無く、この repo は CC0 で公開される。リンク先で見られる。

## 3. 配信元の構造

### 休館日 — `cal.php` (JSON) しか経路が無い

`/calendar/` の HTML には空の `<table id="opac-calendar">` があるだけで、中身は
`/js/libraryHoursKids.js` が JSON API を叩いて描画している。

```
https://www.hanno-lib.jp/cal.php?libraries=<館コード>&term_from=YYYYMM&term_to=YYYYMM
```

```json
{"libraries": [{"code": "02", "name": "こども図書館",
  "term": [{"month": "202608",
            "closing_day": ["2026/08/03", …],
            "event_day":   ["2026/08/01", …]}]}]}
```

**1 リクエスト 1 館。** `libraries=01,02` とまとめて指定すると `event_day` が
空で返る (2026-08-23 実測)。館ごとに分けて叩くこと。

館コードは `libraryHoursKids.js` の `KAN_LIST` が持つ:
`01` 市立図書館 / `02` こども図書館 / `04` 富士見分室 / `06` 名栗分室。

**分室 (04/06) は対象外。** 市のお知らせ (oshirase-13108) によれば名栗・富士見
分室は 2026-04-01 に廃止され、移動図書館も休止している。`cal.php` はまだ 2 か月
分だけ返してくるが、実体が無い。

#### 取得できる範囲は「年度末まで」であって固定の月数ではない

2026-08 に 01/02 とも 8 か月分 (202608..202703) を返したが、**これは
ローリング 8 か月ではない**。`term_from=202704` を要求すると `term` が空で返る
(2026-08-24 実測)。データは **2027-03 = 令和8年度末**で終わっている。過去
(202601〜) は返る。

つまり休館日は**年度単位で登録**されており、取れる月数は観測時期で変わる。
8 月なら 8 か月、翌年 2 月なら 2 か月、4 月に新年度が入れば 12 か月。8 か月と
いう数字は 8 月に観測したことの副産物にすぎない。

この性質は 2 か所に効く。**取得ウィンドウ**は固定の月数で切らず (5 節)、
**件数チェック**は総数の固定値で判定しない (8 節)。分室が 2 か月しか返さない
ことも、ホライズンが固定でない傍証だった。

### イベント — `event_day` → `events.php` → 詳細ページ

```
https://www.hanno-lib.jp/events.php?kind=2&target=general&libraries=<館>&term_from=YYYYMMDD
```

その日のイベント記事のタイトルと詳細 URL を `<article>` 内の `<ul><li><a>` で
返す。`term_to` は**無視される** (1 日分のみ)。`target` は `general` と `kids`
で出力が同一 (絞り込みではない)。ページ自身の JS が `general` を送っているので
それに合わせる。

詳細ページ (`/calendar/<page>.html`) は静的で `Last-Modified` を返すので
`fetch_with_cache()` の条件付き GET が効く。`cal.php` / `events.php` は PHP で
`Last-Modified` を返さない。

**イベントは当月限定ではない。** 2026-08-23 時点で 9 月は 0 件だったが、翌
2026-08-24 には 1 件入った。告知され次第、先の月にも積まれる。したがって
`event_day` は取得ウィンドウ全体を見る。

**イベントが登録されているのはこども図書館 (02) だけ。** 本館 (01) は返ってくる
8 か月すべて 0 件 (2026-08 時点)。これは仕様ではなく現在の運用状態なので、本館側
も同じ経路で見る。

### CI から通ることの確認 (2026-08-24)

`.github/workflows/probe-lib-endpoints.yml` (workflow_dispatch、判定が付いたら
削除する) で実測した。ランナーは米国シカゴ (172.183.133.243)。

| 対象 | 結果 |
|---|---|
| `cal.php` | HTTP 200。`closing_day` / `event_day` が実体として入っている |
| `events.php` | HTTP 200。記事リンクを含む |
| `/calendar/` | HTTP 200 |
| `/calendar/822.html` | HTTP 200 + `Last-Modified` |

商工会議所で踏んだ国外 IP 遮断 (README「商工会議所の REST API は使えない」) は
起きない。**確認を先にやる理由**は、`cal.php` が休館日の唯一の経路だからで、
ここが塞がっていたら取得層の書き直しでは済まず設計そのものが変わっていた。

## 4. カレンダー構成 — 館ごとに分ける

カレンダーは**館ごとに独立**させ、city-tecoli 側で各施設の place_id に紐づける。

| 館 | place_id | 論理名 |
|---|---|---|
| 飯能市立図書館 (山手町19-5) | `ChIJo0ygjPCcJhURjglJPLfCYRs` | `lib-main` / `lib-main.en` |
| こども図書館 (稲荷町25-8) | `ChIJyVn5ejkmGWARKQvc2xVW-F4` | `lib-kids` / `lib-kids.en` |

**英訳する。** 日替わりシェフ (`chef`) を訳していない理由は「店舗ページに i18n
の仕組みが無く、訳文を読む場所が存在しない」で、施設ページも同じ `EntityDetail`
を使う。この点を確認した上で、英訳する判断になった (2026-08-24)。

### `source_type` は 館 × 種別 の 4 つ

`source_type → calendar` のルーティングは 1:1 なので、館を `source_type` に
含める必要がある。種別も分けておく。

| `source_type` | → calendar | uid |
|---|---|---|
| `hanno-lib-main-closed` | `lib-main` | `libmain-closed-<YYYYMMDD>` |
| `hanno-lib-main-event` | `lib-main` | `libmain-event-<ページ名>-<YYYYMMDD>` |
| `hanno-lib-kids-closed` | `lib-kids` | `libkids-closed-<YYYYMMDD>` |
| `hanno-lib-kids-event` | `lib-kids` | `libkids-event-<ページ名>-<YYYYMMDD>` |

種別まで割るのは YAML 2 行の追加で済み、「後から休館日だけ英訳を止める」と
いった調整が UID を変えずにできる。**UID を変えると全件が作り直しになる**。

`<ページ名>` は詳細ページのファイル名から `.html` を落としたもの
(`/calendar/822.html` → `822`、`/calendar/post-84.html` → `post-84`)。配信元が
振っている識別子をそのまま使う。記事タイトルから作らないのは、タイトルが直れば
UID が変わって別イベントになるため。

`<YYYYMMDD>` を付けるのは、1 記事が複数日に出るため (6 節「イベントは 1 記事
1 件ではなく日ごとに 1 件」)。

### カレンダーの作成

`gws` で 3 手順 (作成 → 一般公開 → SA に writer 委託)。コマンドは README
「カレンダーを新規に作る」。`GOOGLE_WORKSPACE_CLI_CONFIG_DIR` を固定すること
(ユーザー OAuth が SA 認証を上書きする)。

所有アカウントは cci / chef と同じ `tecolicom@gmail.com`。本来は「データを管理
している主体のアカウント」が望ましいが、図書館のアカウントは我々に無い。

## 5. クローラは 2 つに分ける

| | 系統 | 写す先 |
|---|---|---|
| `cal-lib-closed-fetch` | **集合同期型** | `cal-cci-chef-fetch` (196 行、`sync_set()` の最小例) |
| `cal-lib-event-fetch` | **追記型** | `cal-cci-event-fetch` |

休館日は配信元が毎回「その月の全体」を出す (取り消しは消えることで表現される)。
イベントは新着が増えていく。README「クローラの 2 系統」がそのまま当てはまる。

1 つに混ぜると、CI のステップ順序の要件 (prune を `--update-manual` より前) が
片方にしか掛からず事故の温床になる。まとめて得られるのは「`cal.php` を 1 回
節約できる」だけで、対価に釣り合わない。

### 取得の流れ

```
cal-lib-closed-fetch
  cal.php?libraries=01&term_from=<今月>&term_to=<+12か月>  → closing_day[]
  cal.php?libraries=02&…                                    → closing_day[]
  → 終日イベント化 → _lib.sync_set()                         2 リクエスト

cal-lib-event-fetch
  cal.php  同上 (event_day[] を取る)                         2 リクエスト
  events.php?…&term_from=<日>  … event_day の日数分
  /calendar/<page>.html を fetch_with_cache … ユニーク記事分
```

**要求は今月の 1 日から 12 か月先まで。返ってきた分だけを扱う。** 過去は取らない。

12 か月は「配信元が持ちうる最大」であって期待値ではない。配信元のデータは年度末で
終わる (3 節) ので、実際に返るのは観測時期次第で 1〜12 か月。**多めに要求するのは
1 リクエストのコストが変わらないから**で、こうしておけば 4 月に新年度が入った
瞬間に自動で拾える。「+7 か月」のような固定値を置くと、年度境界で取りこぼすか、
月数を暦から計算する余計なコードが要る。

1 日あたり計 20 リクエスト前後で、詳細ページだけ 304 が効く。

**`max_event_days` (既定 60) で打ち切る。** `event_day` が異常に増えたときに
`events.php` を無制限に叩かないための暴走防止。`cci-event` の `max_pages` と
同じ発想。打ち切ったらログに残す (黙って切ると「全部見た」と読める)。

## 6. イベントの形

| | 休館日 | イベント |
|---|---|---|
| summary | `🏛 こども図書館 休館` | `📚 夜のおはなし会（8月22日）` |
| 形式 | 終日・単日 | 終日・単日 |
| description | `<館名>は休館です` + カレンダーページ URL | 詳細ページ本文 |
| LLM | 使わない | 長い記事だけ要約 |
| `summary_method` | なし | `full` または `llm-haiku-4-5` |

**summary に館名を残す。** カレンダーが分かれていても、city-tecoli の日次表示は
購読 cal のイベントを所属に関わらず混ぜて出す (city-tecoli README「購読 cal の
日次表示」)。「休館」だけでは意味が通らない。

**休館日に LLM を通さない。** `cal.php` が返すのは日付だけで要約する本文が無い。
決定論的に作れるものに LLM を挟むと `content_hash` が揺れる余地を増やすだけ。

**イベントは短い記事は全文、長い記事だけ要約** (`cal-cci-event-fetch` に倣う)。
こども図書館の記事は実測で数百字と短く、多くは全文になる見込み。全文なら
`summary_method: full` で AI ラベルは付けない (引用扱い)。要約したときだけ冒頭に
「AI による要約 (正確な情報は元記事をご確認ください)」。元 URL はどちらでも末尾
に併記する。

### イベントは 1 記事 1 件ではなく日ごとに 1 件

「8月のおはなしのじかん(8月1・2・8・9・11・15・16・22・23・29・30日）」のような
記事は、`events.php` が該当日それぞれで同じ記事を返す。配信元が「その日の
イベント」として出している形をそのまま写す。

これは「配信元が出しているものはそのまま出す」の帰結
(README「状態 (休館日・開館時間) の扱い」と同じ原則)。

### `rrule` は使わない

`/calendar/` のページには規則が文で書かれている (「まいしゅう げつようび は、
おやすみです」「まいつき さいごのきんようびは おやすみです」)。しかし
`closing_day` には **2026-08-12 (祝日の翌日) が入っており、この規則からは導け
ない**。配信元は規則ではなく個別の日付を列挙している。

README「繰り返し予定 (rrule)」の「配信元が個別の日付を列挙しているだけなら
展開されたまま扱う (規則を推測しない)」に該当する。rrule の節はまさにこの配信元
を想定して書かれたが、実データを見ると発火しない。

## 7. 削除ガード

休館日は集合同期型なので `_lib.plan_set_sync()` のガードが効く。管理下に入るのは
2 館 × 返ってきた月数 × 月 4〜8 件。2026-08 時点で**約 100 件** (8 か月分)。
月数は観測時期で変わる (3 節)。

| 起きうること | 結果 |
|---|---|
| `cal.php` が一時的に短い期間しか返さない | incoming の日付範囲が縮むだけ。範囲外は消さないので過去分は残る |
| `cal.php` が 200 で空の JSON を返す | incoming が空 → 日付範囲も空 → **1 件も消えない** |
| 月が変わって前月が範囲外になる | 同上。前月の休館日は残る |
| 配信元が本当に休館日を取り消した | 消える。これが正しい動作 |

`max_delete` は**既定の 10 のまま**。上の 3 つで大量削除の経路が塞がっている
以上、上げる根拠がない。

`status: canceled` は使わない。ページから消えた理由を我々は知り得ない
(README「削除ガード」の「根拠のない状態表示は行わない」)。

CI では **prune を `fetch --update-manual` より前**に置く。逆にすると、削除した
はずの予定が不可侵な手動イベントとして蘇生する。

## 8. 件数チェックは 2 つのクローラで意味が違う

- **休館日**: **館ごと・返ってきた月ごとに 3 日以上** (`--min-days-per-month 3`)。
  総数の固定値は使えない。取れる月数が観測時期で 1〜12 か月に変わる (3 節) ので、
  「合計 20 件」のような閾値は 2027 年 2〜3 月に正常時でも赤を出す。**館ごとに
  見る**のも必須で、合計で判定すると 02 が丸ごと空でも 01 の分で閾値を超えて
  半分の欠落が静かに通る。実測は月 4〜8 件なので 3 は十分下に取ってある。
- **イベント**: **件数では測れない。** `event_day` が 0 件の期間は普通にあり
  (本館 01 は現時点で返る月すべて 0)、0 を異常とすると常時赤になる。かわりに
  **`cal.php` の応答が JSON として読め `term` を含むこと**を疎通の証拠として
  検査する。

`--min-items 0` を避けよという指示 (skill「引き上げる前に」) の趣旨は「1 件も
取れない異常を CI が緑のまま通すな」であって、件数という手段そのものではない。
イベント側は疎通でその趣旨を満たす。取得層が死んだときは 0 件ではなく「JSON が
読めない」形で出る。

## 9. テスト

### golden (ネットワーク非依存、CI 実行)

**スタブは最下層に当てる。** `cal.php` / `events.php` / 詳細ページの取得関数
だけを差し替え、JSON 解析も HTML 解析も本物を走らせる。上位を丸ごと差し替えると
今回書く解析コードが 1 行も走らないまま緑になる。

1. 初回取込 — 休館日 N 件が生成される
2. 配信元から消えた休館日が削除される
3. **範囲外の過去は削除されない** (7 節のガード)
4. イベント — `event_day` → `events.php` → 詳細ページ → YAML

### ユニット

- 期間ウィンドウの計算 (今月 1 日 → +12 か月、年またぎ)
- `--min-days-per-month` の判定 (館ごと・月ごと。返ってきた月だけを見る)
- `max_event_days` の打ち切り
- `events.php` の HTML から記事タイトル + URL を取る処理
- `cal.php` の JSON から館ごとの `closing_day` / `event_day` を取る処理

## 10. 登録先 — どれか 1 つ欠けても静かに動かない

| 場所 | 書くこと |
|---|---|
| `calendar/sources.yaml` | `lib-closed` / `lib-event` の 2 節。館コード → 館名・`uid_prefix`・`source_type` の対応表、`page_url` / `cal_url` / `events_url`、`url_host_allowlist`、`url_path_prefix`、取得ウィンドウ (`months_ahead: 12`)、`max_event_days: 60`、`max_delete: 10` |
| `calendar/bin/cal-lib-closed-fetch` | 集合同期型クローラ。`--min-days` を持つ |
| `calendar/bin/cal-lib-event-fetch` | 追記型クローラ |
| `calendar/city.yaml` の `calendars` | `lib-main` / `lib-main.en` / `lib-kids` / `lib-kids.en`。コメントに place_id と所有アカウントを残す |
| `calendar/city.yaml` の `source_type_to_calendar` | 4 行。**忘れると YAML は増えるがカレンダーに出ない** |
| `.github/workflows/cal-daily.yml` | Crawl 2 ステップ + closed の prune。event 側に `ANTHROPIC_API_KEY` |
| `calendar/tests/run-golden` | `_setup_lib_closed` / `_setup_lib_event` + 4 シナリオ (9 節) |

`--min-days` は休館日クローラ固有の名前にする。既存クローラの `--min-items` /
`--min-tours` / `--min-news` と同じ役割だが、数えているのが「日」なので名前を
実体に合わせる。

## 11. CI 配線

`cal-daily.yml` に 2 ステップを**既存クローラの後ろ**に置く。遮断は 403 の連発で
IP ごと締め出される形で起き、同じランナーから動く**他のクローラまで巻き添えで
落ちる** (2026-08-20 実測)。新顔を先頭に置くと既存ソースを人質に取ることになる。

各ステップは `|| echo "<name>" >> "$RUNNER_TEMP/crawl-failures.txt"` で配線する
(裸の `run:` にすると 1 つの失敗でジョブが止まり、他ソースが反映されない)。
イベント側には `ANTHROPIC_API_KEY` を渡す — 渡さないと要約が本文そのままに
変わり `content_hash` が動く。

休館日の prune は `fetch --update-manual` より前 (7 節)。

## 12. 進める順序

1. カレンダー 4 つを `gws` で作成し `city.yaml` に登録
2. `cal-lib-closed-fetch` + テスト (LLM 不要・決定論的。ここまでで価値が出る)
3. `cal-lib-event-fetch` + テスト
4. CI 配線
5. **初回取込は手元で実行して差分を確認**。`.http-cache.json` の新規エントリは
   commit しない (最初の CI 実行が 304 で全 skip する)
