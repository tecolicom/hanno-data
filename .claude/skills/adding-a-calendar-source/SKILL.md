# 新しい配信元を取り込む

事実の正典は `calendar/README.md` (1000 行超)。**このスキルは内容を繰り返さない** —
決める順序、判断の基準、登録し忘れる場所だけを持つ。詳細は各節へ飛ぶこと。

## 先に決める 4 つ

後から変えると作り直しになる順に並べている。**コードを書く前に 4 つとも答えを出す。**

### 0. 取り込んでよいか

配信元の利用条件を先に見る。`robots.txt`、サイトの利用規約、転載の可否。
**この repo は CC0 で公開される**ので、権利を主張している出典の本文をそのまま
持ち込むと矛盾する。要約の程度は `docs/ai-content-policy.md` の方針に合わせる。

判断がつかないときは取り込まずに聞く。city-tecoli には利用規約を理由に本番配信を
止めた前例がある (`global-cals.yaml` の `preview_only`)。

### 1. 系統はどちらか

配信元が**毎回「全体」を出す**なら集合同期型、**新着が増えていく**なら追記型。
→ README「クローラの 2 系統」「削除ガード」「prune は fetch --update-manual より前に置く」

**写す先**: 集合同期型なら `cal-cci-chef-fetch` (196 行、`_lib.sync_set()` を使う最小例)。
追記型なら `cal-cci-event-fetch` (RSS + LLM 要約) か `cal-oshirase-fetch` (世代管理・差分要約
まで入った重い例)。ゼロから書かない。

判定を誤ると: 追記型として作った集合同期型のソースは、予定が取り消されても
カレンダーに残り続ける。逆に集合同期型として作った追記型は、一覧から溢れた
古い記事を「取り消された」と誤解して消す。

### 2. その経路は CI から通るか

**ローカルで通ったことは、CI から通る根拠にならない。** GitHub Actions のランナーは
国外 IP で、日本のレンタルサーバは国外からの REST を既定で遮断していることがある。
HTML と RSS は開いたまま REST だけ 403 になる、という形で現れる。
→ README「商工会議所の REST API は使えない → RSS に切替済み」

**実装前に CI から 1 回叩いて確かめる。** 手元で作り込んでから塞がっていると分かると、
取得層を丸ごと書き直すことになる (2026-08-20 に実際に発生)。

### 2.5 何を落とすか — 落とさない

**配信元が出しているものは、そのまま出す。** 休館日のように他所 (Google Places) でも
取れる情報でも落とさない。「これは要らない」と我々が選り分けるのは立ち入りすぎ
→ README「状態 (休館日・開館時間) の扱い」。

規則そのもの (「毎週土日祝」) が書かれているなら、N 件に展開せず `rrule` を使う
→ README「繰り返し予定 (rrule)」。実装済み・使用例ゼロなので存在に気づきにくい。

### 3. 英訳するか

判断基準は「**その英訳を読む場所が存在するか**」。日次ポータルや暦体ページに出るなら
訳す。店舗ページのように i18n が無い面にしか出ないなら訳さない
(`cal-translate-en` の `NO_TRANSLATION_SOURCE_TYPES` に入れる)。

## 登録先 (どれか 1 つ欠けても静かに動かない)

| 場所 | 何を書くか | 忘れると |
|---|---|---|
| `calendar/sources.yaml` | `uid_prefix` / `source_type` / `summary_prefix` / URL | クローラが起動時に落ちる (すぐ気づく) |
| `calendar/bin/cal-<name>-fetch` | クローラ本体 | — |
| `calendar/city.yaml` の `calendars` | logical name → カレンダー ID | apply 先が無い |
| `calendar/city.yaml` の `source_type_to_calendar` | `source_type` → logical name | **YAML は増えるがカレンダーに出ない** |
| `.github/workflows/cal-daily.yml` | Crawl ステップ。LLM 要約するなら `ANTHROPIC_API_KEY` を env に渡す | 手で回すまで永久に更新されない (キー無しだと要約が本文そのままに変わり `content_hash` が動く) |
| `calendar/tests/run-golden` | `_setup_*` + シナリオ | 出力が壊れても誰も気づかない |

集合同期型ならこれに加えて、`cal-daily.yml` の **prune を `fetch --update-manual` より
前**に置く (順序自体が設計。README の該当節を読むこと)。

## 引き上げる前に

- **`--min-items` (または `--min-events`) は 1 以上。** 0 は「1 件も取れない異常を CI が
  緑のまま通す」設定。2026-08-20 の REST 遮断はこれで見逃された。
- **golden のスタブは取得の最下層に当てる。** 上位関数を丸ごと差し替えると解析コードが
  走らないまま緑になる → README「テスト (golden 網)」の該当項。
- **`content_hash` に要約手法や生成条件を混ぜない。** 混ぜると手法を変えた瞬間に全件の
  ハッシュが変わり、カレンダーが氾濫する。
- 初回取込は**必ず手元で実行して差分を見る**。CI に初回を任せない。ただし
  **`.http-cache.json` の新規エントリは commit しない** — 最初の CI 実行が 304 で
  全 skip する → README「HTTP Conditional GET」の警告。
- **遮断されうる配信元は、安定しているものの後ろに置く。** 遮断は 403 の連発で IP ごと
  締め出される形で起き、同じランナーから動く**他のクローラまで巻き添えで落ちる**
  (2026-08-20 実測)。新顔を先頭に置くと、既存のソースを人質に取ることになる。
- **CI のステップは `|| echo "<name>" >> "$RUNNER_TEMP/crawl-failures.txt"` で配線する。**
  裸の `run:` にすると 1 つのクローラの失敗でジョブが止まり、他ソースが反映されない。
  ジョブ末尾の "Report crawler failures" がまとめて赤にする。

## よくある事故

| 事故 | 原因 | 防ぎ方 |
|---|---|---|
| 削除したはずの予定が不可侵な手動イベントとして蘇生 | prune が `--update-manual` の後 | ステップ順序を守る |
| 取得側の障害で大量削除 | 削除上限を緩めた | `max_delete` の既定は 10。上げるなら根拠を持つ (実績: 95 件の消失を阻止) |
| golden が緑なのに本番で壊れる | スタブが高すぎる層 | 「今回書いたコードは走るか」で判断 |
| ローカルで動いたのに CI だけ 403 | 国外 IP からの REST 遮断 | 経路を決める段階で CI から叩く |
| 既存の翻訳が全部消える | YAML を消してからクローラ再実行 | 既存ファイルを置いたまま実行する |

## 新しいカレンダーを作る必要があるとき

カレンダーは**そのデータを管理している主体のアカウントに作る** (名前と実態の不整合を
防ぐ)。作成 → 一般公開 → SA に writer 委託の 3 手順は `gws` で完結する。
コマンドは README「カレンダーを新規に作る」にある。

`gws` を使うときは `GOOGLE_WORKSPACE_CLI_CONFIG_DIR` を固定すること — ユーザー OAuth が
SA を上書きする (README「落とし穴: ユーザー OAuth が SA 認証を上書きする」)。
